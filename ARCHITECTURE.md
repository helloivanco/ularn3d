# Architecture

## Runtime

The game is a static Vite application with an optional offline Electron desktop host. Three.js renders the world with a perspective camera, shadows, fog, procedural meshes, and pointer controls. There is no application backend.

The public website keeps browser play at `/` and offers a separate static guide at `/about/`. `public/about/index.html` and its stylesheet are copied directly into the build; `vite.config.js` uses multipage mode and directory-index middleware so development and preview serve the guide at its production URL. `public/site-runtime.js` identifies the browser or `ularn:` desktop host and hides web-only download controls inside the desktop application.

`public/engine/` contains the original JavaScript Larn/Ularn source and assets. `scripts/build-engine.mjs` concatenates its classic scripts in upstream load order, then appends `src/bridge.js`, producing `public/engine/game.js`. The Vite build copies this bundle and other public assets into `dist`.

## Authority and state

The original engine owns level generation, player attributes, items, monsters, movement, turns, combat, spells, shops, traps, time limits, and endings. The 3D UI sends ordinary engine commands through `window.ularn.key()`. It does not independently simulate gameplay.

The bridge exposes `start`, `snapshot`, `key`, `openToward`, `save`, `hasSave`, `interruptTravel`, and `setAutoLoot`. Snapshot adds inventory slots/equipment, actual effect timers, map glyphs, weapon families, and weakly held monster presentation identities/facing. Known, unmasked staircase tiles also receive direction and blocked-state metadata derived from the existing `stairs.js` dead-end conditions; blocked stair names append `(dead end)`. Snapshot construction filters unexplored tiles, hidden traps, invisible monsters, and blindness using the engine's knowledge flags and visibility checks. The presentation never treats its meshes as authoritative collision data.

`src/world.js` renders known tiles and follows the player. `src/materials.js` caches procedural surface maps and materials. `src/models.js` builds the player, buildings, creature families, terrain objects, and items from local procedural geometry. `src/main.js` owns HUD updates, input, contextual-menu layout, known-tile pathfinding, minimap, camera controls, sound, and start/pause/help flows. Clicking a staircase underfoot dispatches the original `<` or `>` command according to its tile identity. Stair models display direction-specific steps or rubble and a cross for intentional dead ends. The usable Volcano 1 exit is a separate shaft tile labeled `SURFACE SHAFT`; its behavior is not inferred from the blocked staircase rules.

`src/monster-art.js` caches artwork by exact species. Most species use the original bundled sprites, including Ularn and revealed-monster variants. Species 1 uses `public/art/monsters/lemming.png`, an original generated natural rodent illustration whose prompt is recorded in [docs/art/lemming.prompt.md](docs/art/lemming.prompt.md). This presentation-only override leaves lemming identity, stats, behavior, spawn rules, and the classic `public/engine/img/m1u.png` sprite intact. The texture is loaded once and shared between lemmings. Camera-facing planes mirror according to heading, with ground direction markers. Monster groups retain identity across tile movement. All monster artwork remains single-view with facing mirrors, rather than eight-direction animation sheets.

`src/item-art.js` caches presentation artwork for floor loot under `public/art/items/` (97 unique sprites). Generation provenance is recorded in [docs/art/items.prompt.md](docs/art/items.prompt.md). Covered categories are weapons, armor, rings, belt of striking, potions (full table by `arg`), scrolls (full table by `arg`), books, cookies, artifacts, gems, and gold piles. The bridge snapshot exposes item `arg` so potion/scroll variants resolve correctly. Camera-facing planes mirror left/right as the overhead camera orbits. Engine item identities, stats, spawn rules, and classic `public/engine/img/o{id}.png` tiles remain unchanged; unlisted tiles still use procedural meshes from `itemModel`.

`src/hud.css` lays out the bottom controls, large symbol map, persistent inventory, and right-hand effect rail. Inventory/effect DOM updates use content signatures. `src/audio.js` synthesizes separate weapon families and all spell cues, bounds voices at 24, and disconnects sources/filters/gains after playback or suspension. `src/combat-effects.js` owns a six-slot, fixed-buffer pool for casting rings and visible projectile segments. Bridge `ularn:combat` events report accepted casts, actual weapon attempts, and only explored, currently visible projectile segments. Cancelled/failed casts generate no visual or audio feedback. Animation never simulates damage.

`src/icons.js` defines 35 original SVG interface icons on a shared 24-unit grid. Static icon slots mount once; the sound toggle and hero emblem update only when their state changes. Icons inherit control colors, remain hidden from assistive technology, and never intercept pointer input. Buttons retain text labels or explicit accessible names. The site favicon uses the same Ularn sigil. No icon fonts, external icon requests, or additional dependencies are required.

Native engine context buttons and its terminal panels remain available for the complete set of original commands. The bridge namespaces their IDs, replaces the engine's absolute page layout, and disables upstream telemetry and online services. The classic fallback uses a small `offline.js` hosting adapter for the same network isolation.

The vendor source has small adapters: `store.js` only advertises replay links when recording is enabled, and `explore.js` rechecks cancellation after awaited approach animations. The latter prevents an interrupted native explorer from taking a queued step after a pause or manual command. Gold is always collected; auto-loot only applies to other items. Spell resolution offers a presentation-only acceptance hook after its rule checks. Small copy edits in `object.js` explicitly identify up/down stairs and dry fountains; `fountain.js` announces that draining leaves no water. Fountain prompts use “wash.” The original draining checks still replace the fountain tile with `ODEADFOUNTAIN`, and the existing floor-state save path persists that object unchanged. Combat, monster AI, stair-transition rules, and progression rules are otherwise unchanged.

Known floor and wall tiles are GPU-instanced from 12-triangle boxes. Static terrain and buildings in both the title scene and gameplay are merged by material; reusable model geometries are shared and kept to low segment counts (boxes instead of rounded boxes, 80-triangle orbs, 128-triangle rings). Distant title and town terrain does not cast shadows. Replaced merged geometry and landmark textures are disposed when levels change. Shadows update when the scene or nearby cutaway walls change. Balanced rendering skips the PMREM environment, MSAA, and extra torch point lights; cinematic restores those plus bloom and output color conversion. On context loss, the renderer releases GPU resource registrations while retaining CPU-side geometry and materials. Restoration reuploads that artwork and regenerates the reflection environment when cinematic. This prevents stale-handle deletion errors during later WebKit level changes, quality changes, and resizes. Read-only `ularnGraphics.metrics()` reports rendering, frame limits, idle state, sprite/effect pools, active lights, and GPU resource counts for diagnostics. The WebGL renderer requests a high-performance GPU. Camera orbit, zoom, and walk follow `requestAnimationFrame` without an extra timeout throttle so panning stays vsync-smooth; Balanced still stops drawing once the scene settles, and Cinematic idles at 12 FPS. Hidden windows stop frame scheduling. Floor-loot sprites flood-fill pale generated cards out of their alpha so items do not sit on a white plate. Transient spell and fountain lifetimes use wall time to expire correctly even on slow hardware. Per-frame work faces only billboard sprites and draining fountains rather than walking every tile group.

## Persistence

The autosave key is `ularn3d.expedition.v1`. Saves contain a version, the engine's complete `GameState`, and optional equipped-slot indices, compressed with the bundled LZString library. Equipped-slot metadata distinguishes identical items so the exact wielded/worn objects survive reload; existing version-one saves without this metadata remain readable. Saving only happens between stable turns: never during a blocking callback, animation, or after death. Autosaves coalesce over two seconds, bounding compression work during repeated input. Manual and exit saves remain synchronous to avoid losing pending state. The original `S` command is adapted to save without invoking the legacy save-and-die path.

Resume calls the original `loadState` after structural validation, avoiding legacy save deletion. Each start attempt resets monster-template combat values to their originals; both new games and resumes then run the original difficulty calculation exactly once. Saved individual monsters retain their own health and combat values. All original save-slot, backup, checkpoint, and winner-mail keys are redirected to a `ularn3d.legacy.` prefix; periodic checkpoints and endings therefore preserve classic save slots. Preferences and local leaderboard handling remain as before. Save errors dispatch a presentation event immediately. Informational telemetry is disabled; original error/warning diagnostics remain visible in the local browser console. The 3D door shortcut sends the original Open command and its requested direction synchronously; it sends no direction when the original rules reject Open. Enter/Space activate focused interface controls through the browser while other gameplay commands retain their engine mapping. The UI interrupts both its own route timer and the native engine explorer when pausing, opening help, or hiding the page. Input is also gated while a dialog is open or graphics are unavailable. Original local score handling is retained. Global scores, recorded replays, and the weekly challenge service are not attached to this fork.

## Deployment

`npm run build` produces `dist`; Vercel serves those static files. Public entry points are [browser play](https://ularn-3d.vercel.app/), the [static guide](https://ularn-3d.vercel.app/about/), and the optional [Windows executable](https://ularn-3d.vercel.app/downloads/Ularn.windows.exe). The classic fallback is served directly from `/engine/larn_local.html`. These are real files and directory indexes, so no SPA wildcard rewrite is needed. Source scripts and the original engine license are kept with the project. `package-lock.json` pins dependencies. Production deploys for `helloivanco/ularn3d` target the Vercel project that serves `ularn-3d.vercel.app`.

The game and guide contain canonical URLs, descriptions, Open Graph/Twitter metadata, and JSON-LD. Their shared social image is `public/social/ularn.png`. `public/robots.txt` points to `public/sitemap.xml`, which lists `/` and `/about/`. `vercel.json` redirects duplicate document/guide URLs to their canonical paths, marks `/engine/` and `/downloads/` responses as non-indexable, and sends attachment/content-type headers for `Ularn.windows.exe`. The published URL path is stable across releases; Vercel redirects it to the GitHub Release asset `Ularn-${version}.windows.exe` for the current `package.json` version so Git deploys cannot omit the binary. The play page, field-guide footer, JSON-LD, and Electron package display that same version. Each product release runs `npm version` so those surfaces cannot keep a previous number.

The Electron host in `desktop/main.cjs` serves `dist/` through `ularn://game/`, with a sandboxed renderer, no Node integration, a persistent `Ularn` profile, and remote requests disabled. `desktop/protocol.cjs` confines requests to packaged assets and resolves directory URLs such as `/about/` to their `index.html`. Closing the app saves the last stable turn before flushing storage. Desktop and browser saves have separate storage origins.

`desktop/electron-builder.yml` produces the self-contained Windows x64 portable `Ularn.windows.exe`, plus optional app-folder, ZIP, and installer targets. Its pinned NSIS `1.2.1` bundle includes a native Apple Silicon compiler, so the portable executable can be cross-built without Rosetta. `npm run desktop:package:win:portable` builds the game and executable; `npm run desktop:verify:portable` extracts that executable, verifies all embedded runtime files and game assets against the local build, and writes its SHA-256 sidecar. The Windows GitHub Actions workflow builds and verifies artifacts, and a push to `main` publishes the versioned portable file as a GitHub Release. See [DESKTOP.md](docs/DESKTOP.md).

The executable is Git-ignored, so a source-only Vercel Git build cannot embed it. The site keeps `/downloads/Ularn.windows.exe` and redirects that path (and the checksum) to the GitHub Release for the current `package.json` version. Desktop packaging still excludes `dist/downloads/`, preventing recursive executable payloads; `.vercelignore` excludes the separate `release/` working directory.

Optional local prebuilt deploys can still stage a verified executable under `public/downloads/` before `vercel build --prod`. The exact commands are in [README.md](README.md#build-and-vercel). GitHub Releases are the hosted download used by production.

## Validation boundaries

Playwright verifies actual browser input, presentation state, and serialized reloads. Fixtures seed difficult-to-reach scenarios such as demon visibility, death, and quest completion, then exercise the original callbacks. No gameplay cheats or test-only endpoints are included in the UI. Automated verification reduces regression risk; it cannot prove that a large random roguelike has no defects.

Site checks cover the static guide, metadata, sitemap, and download links. Desktop tests cover local asset routing, traversal rejection, renderer isolation, first-launch storage creation, and saving through a complete Electron restart. Portable extraction verification proves the runtime payload is self-contained; macOS tests do not execute the Windows binary.
